# Docker в проекте Research Scout

Практическая документация по настройке, запуску и диагностике Docker на
основе работы над Research Scout.

## 1. Что запущено

Проект использует Docker Compose для запуска нескольких связанных
сервисов:

  -------------------------------------------------------------------------
  Сервис                  Назначение              Доступ
  ----------------------- ----------------------- -------------------------
  `frontend`              React/Vite-интерфейс    `http://localhost:5173`

  `backend`               FastAPI, HTTP API       `http://localhost:8000`

  `researcher`            CLI-обработка и анализ  запускается командой
                          источников              

  `searxng`               Поиск через SearXNG     `http://localhost:8080`
  -------------------------------------------------------------------------

Docker Compose создаёт общую сеть. Поэтому контейнеры обращаются друг к
другу по имени сервиса, а не через `localhost`.

## 2. `Dockerfile` и `compose.yaml`

### Dockerfile

`Dockerfile` описывает, как собрать образ одного приложения: базовый
образ, рабочую папку, установку зависимостей, копирование файлов и
команду запуска.

Типичный порядок инструкций:

``` dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

Это пример структуры, а не утверждение о точном содержимом Dockerfile в
текущей версии проекта. Для FastAPI команда запуска обычно задаётся
через `CMD` или в `compose.yaml`.

### compose.yaml

`compose.yaml` описывает сервисы, их образы или сборку, порты,
переменные окружения, тома и связи между контейнерами. Вместо запуска
каждого контейнера вручную проект поднимается одной командой.

Принципиальные части конфигурации Research Scout:

``` yaml
services:
  backend:
    # build / image и настройки приложения
    ports:
      - "8000:8000"
    volumes:
      - ./data:/app/data
    environment:
      DATABASE_PATH: /app/data/research.db

  researcher:
    # отдельный сервис для CLI-обработки
    volumes:
      - ./data:/app/data
    environment:
      DATABASE_PATH: /app/data/research.db

  searxng:
    image: searxng/searxng:latest
    ports:
      - "8080:8080"
    volumes:
      - ./settings.yml:/etc/searxng/settings.yml
    restart: unless-stopped
```

Это сокращённый фрагмент для объяснения ключевых настроек; он не
заменяет полный файл проекта.

## 3. Сеть контейнеров: важное различие между `localhost` и именем сервиса

Внутри контейнера `localhost` указывает на сам этот контейнер. Поэтому
backend не должен обращаться к SearXNG по `http://localhost:8080`.

В проекте используется адрес:

``` python
SearchClient(base_url="http://searxng:8080")
```

-   Из браузера на компьютере: `http://localhost:8080`.
-   Из другого контейнера Compose: `http://searxng:8080`.
-   `searxng` --- DNS-имя сервиса в сети Compose.

Та же логика действует для остальных сервисов: порты, опубликованные на
хост, нужны для доступа с компьютера; контейнеры общаются между собой по
именам сервисов и внутренним портам.

## 4. Тома и данные

В проекте используется bind mount:

``` yaml
volumes:
  - ./data:/app/data
```

Папка `data` на компьютере связана с `/app/data` внутри контейнера. Это
позволяет backend и researcher работать с одной SQLite-базой, а данным
сохраняться после пересоздания контейнера.

Путь к базе:

``` text
DATABASE_PATH=/app/data/research.db
```

Для конфигурации SearXNG также используется bind mount:

``` yaml
- ./settings.yml:/etc/searxng/settings.yml
```

Практический вывод: если нужно, чтобы контейнер читал файл из проекта,
проверьте, какой путь реально смонтирован в `compose.yaml`.
Редактирование файла на хосте не поможет, если контейнер использует
другой том или другой путь.

## 5. Команды, которые использовались

Запустить сервисы в фоне:

``` powershell
docker compose up -d
```

Пересобрать образы и запустить сервисы:

``` powershell
docker compose up -d --build
```

Пересобрать только backend и researcher:

``` powershell
docker compose up -d --build backend researcher
```

Посмотреть состояние сервисов:

``` powershell
docker compose ps
```

Посмотреть логи:

``` powershell
docker compose logs -f backend
docker compose logs -f searxng
```

Проверить сетевую доступность SearXNG из backend:

``` powershell
docker compose exec backend python -c "import requests; print(requests.get('http://searxng:8080', timeout=5).status_code)"
```

Запустить researcher как отдельную одноразовую задачу:

``` powershell
docker compose run --rm researcher
```

`run --rm` создаёт контейнер для команды и удаляет его после завершения.
Это удобно для CLI-задачи, которая не должна постоянно работать как
веб-сервис.

Остановить сервисы:

``` powershell
docker compose down
```

## 6. Реальный случай: SearXNG возвращал 403

При проверке URL `http://localhost:8080/search?q=test&format=json`
SearXNG возвращал `403`. В логах также появлялось сообщение об
отсутствии `X-Forwarded-For` и `X-Real-IP`.

Во время диагностики выяснилось, что изменения `settings.yml` в папке
проекта не попадали в конфигурацию контейнера, потому что использовался
named volume для `/etc/searxng`. Конфигурацию изменили на прямое
монтирование файла:

``` yaml
volumes:
  - ./settings.yml:/etc/searxng/settings.yml
```

В `settings.yml` для поиска JSON были добавлены форматы:

``` yaml
use_default_settings: true
search:
  formats:
    - html
    - json
```

После изменения конфигурации контейнер пересоздали. Позже сетевое
соединение из backend проверили отдельно и получили HTTP `200`.

Полезный порядок диагностики в похожей ситуации:

1.  Проверить `docker compose ps`.
2.  Посмотреть `docker compose logs -f searxng`.
3.  Проверить, какой файл конфигурации смонтирован в контейнер.
4.  Проверить доступ к сервису из нужного контейнера.
5.  После изменения конфигурации пересоздать соответствующий сервис.

HTTP `200` от корневого URL подтверждает доступность сервиса, но сам по
себе не доказывает, что поиск и JSON-ответ работают правильно.

## 7. Docker Model Runner и Mistral

Отдельно проверена локальная модель:

``` powershell
docker model run mistral:7B-Q4_0
```

Модель отвечает, поэтому Docker Model Runner и сама модель проверены
отдельно. Это ещё не гарантирует, что приложение Research Scout
правильно вызывает LLM: интеграцию приложения нужно проверять через его
`LLMClient` или соответствующий API-путь.

## 8. Как разбирать проблемы

Проверяйте по слоям, чтобы не смешивать разные неисправности:

1.  **Контейнер:** запущен ли сервис (`docker compose ps`)?
2.  **Логи:** нет ли ошибки старта (`docker compose logs ...`)?
3.  **Сеть:** доступен ли адрес сервиса из контейнера-клиента?
4.  **Конфигурация:** смонтирован ли ожидаемый файл и читаются ли
    переменные окружения?
5.  **Приложение:** работает ли конкретный endpoint или функция?
6.  **Данные:** смотрят ли backend и researcher на одну базу?

## 9. Коротко: что запомнить

-   `Dockerfile` описывает сборку образа приложения.
-   `compose.yaml` связывает сервисы и задаёт порты, переменные, тома и
    сеть.
-   `localhost` внутри контейнера --- это сам контейнер.
-   Между сервисами Compose обращайтесь по имени сервиса, например
    `searxng:8080`.
-   Bind mount связывает файл или папку проекта с путём в контейнере.
-   После изменения кода или Dockerfile используйте сборку с `--build`;
    после изменения конфигурации проверьте, что контейнер действительно
    читает этот файл.
-   Проверяйте контейнер, сеть, конфигурацию и логи по отдельности.
