# LLM в Research Scout

Документация основана на текущих файлах `config.py`, `client.py` и
`analyzer.py`.

## 1. Общая схема

``` text
config.py
  адрес API и имя модели
       |
       v
client.py — LLMClient
  отправляет запрос к модели
       |
       v
analyzer.py — ArticleAnalyzer
  готовит промпт для оценки статьи
       |
       v
  текстовый результат анализа
```

Модель Mistral проверена отдельно командой:

``` powershell
docker model run mistral:7B-Q4_0
```

Это подтверждает, что модель запускается и отвечает через Docker Model
Runner. Работу всей интеграции приложения следует проверять отдельно.

## 2. Настройки: `app/config.py`

В текущем файле указано:

``` python
LM_STUDIO_URL = "http://model-runner.docker.internal/engines/v1"
MODEL_NAME = "ai/mistral:7B-Q4_0"
```

-   `LM_STUDIO_URL` --- адрес API, к которому подключается клиент.
-   `MODEL_NAME` --- идентификатор модели, передаваемый в запросе.

Хотя переменная называется `LM_STUDIO_URL`, заданный адрес указывает на
Docker Model Runner. При изменении адреса важно проверить, откуда
запускается Python-код и доступен ли ему этот hostname.

В конфигурации также есть:

``` python
SEARXNG_URL = "http://localhost:8080"
```

Эта настройка относится к поиску, а не к LLM.

## 3. Клиент: `app/llm/client.py`

Класс `LLMClient` создаёт клиент библиотеки `OpenAI`:

``` python
self.client = OpenAI(
    base_url=LM_STUDIO_URL,
    api_key="lm-studio",
)
```

Здесь используется OpenAI-совместимый интерфейс. Значение `api_key`
задано в коде как строка для клиента; по одному этому фрагменту нельзя
сделать вывод, что сервер проверяет настоящий ключ.

Метод `ask(prompt)` отправляет запрос:

``` python
response = self.client.chat.completions.create(
    model=MODEL_NAME,
    messages=[
        {"role": "user", "content": prompt}
    ],
)

return response.choices[0].message.content
```

Таким образом, метод принимает строку с промптом и возвращает текст
ответа модели.

### Что важно знать о текущей реализации

-   Отправляется одно сообщение с ролью `user`.
-   Отдельные системные инструкции в структуре `messages` не
    используются; инструкции анализа включены в сам промпт.
-   В показанном коде нет явной обработки сетевых ошибок или ошибок API.
-   Не задан явный тайм-аут.
-   Код предполагает, что ответ содержит `choices[0].message.content`.

Это описание текущего кода, а не утверждение, что запросы обязательно
будут завершаться ошибкой при любых нестандартных ответах.

## 4. Анализ статьи: `app/llm/analyzer.py`

`ArticleAnalyzer` создаёт `LLMClient` и предоставляет метод:

``` python
analyze(title: str, content: str) -> str
```

Метод формирует промпт для оценки источника как потенциальной истории
для англоязычного YouTube-канала.

Промпт требует использовать только предоставленную информацию, не
придумывать факты и считать утверждения непроверенными, если в тексте
нет подтверждений.

Ожидаемый формат ответа состоит из четырёх полей:

  Поле          Что должно содержать
  ------------- ----------------------------------------------------
  `STORY`       Краткое описание истории в 1--2 предложениях
  `HOOK`        Что необычного или интересного в истории
  `POTENTIAL`   Оценка `High`, `Medium` или `Low`
  `VERIFY`      Одно ключевое утверждение для независимой проверки

В промпт передаётся заголовок и не более первых 5000 символов текста:

``` python
TITLE:
{title}

SOURCE TEXT:
{content[:5000]}
```

Следовательно, модель анализирует не обязательно всю статью: длинный
материал обрезается до первых 5000 символов.

## 5. Путь данных

1.  Код приложения получает заголовок и текст источника.
2.  Вызывается `ArticleAnalyzer.analyze(title, content)`.
3.  Анализатор формирует промпт с заголовком и текстом статьи.
4.  `LLMClient.ask(prompt)` отправляет запрос модели.
5.  Клиент возвращает текст ответа.
6.  Вызывающий код получает результат и может сохранить или показать
    его.

Последний шаг --- сохранение или отображение --- зависит от вызывающего
кода; в `analyzer.py` сам по себе результат не сохраняется.

## 6. Как проверять LLM по слоям

**Проверка 1 --- модель.**

``` powershell
docker model run mistral:7B-Q4_0
```

Это уже проверено: модель отвечает.

**Проверка 2 --- клиент приложения.**

Проверить, что Python-код может обратиться к настроенному API и получить
ответ через `LLMClient.ask(...)`.

**Проверка 3 --- анализатор.**

Передать тестовые `title` и `content` в `ArticleAnalyzer.analyze(...)` и
проверить, что результат содержит `STORY`, `HOOK`, `POTENTIAL` и
`VERIFY`.

**Проверка 4 --- полный сценарий.**

Запустить обычный процесс Research Scout и убедиться, что результат
анализа проходит дальше по приложению и сохраняется там, где это
предусмотрено.

Успешный запуск модели не гарантирует, что адрес API, модель, сетевой
доступ контейнера и код приложения настроены корректно одновременно.

## 7. Текущие ограничения, видимые в коде

-   Результат анализа --- обычная строка, а не проверенный
    структурированный объект.
-   Формат ответа задаётся инструкцией в промпте; код не проверяет
    наличие всех четырёх полей.
-   Текст источника ограничен 5000 символами.
-   В `LLMClient` нет явной обработки исключений, повторных попыток или
    тайм-аута.
-   Промпт просит не придумывать факты, но сам по себе промпт не
    гарантирует фактическую точность. Поле `VERIFY` как раз
    предназначено для выделения утверждения, которое нужно проверить
    независимо.

## 8. Краткая памятка

-   `config.py` --- адрес API и имя модели.
-   `client.py` --- отправка запроса и получение текста.
-   `analyzer.py` --- задача и формат анализа статьи.
-   `docker model run mistral:7B-Q4_0` проверяет модель отдельно от
    приложения.
-   Для проверки интеграции нужно отдельно протестировать `LLMClient`,
    затем `ArticleAnalyzer`, затем полный сценарий Research Scout.
